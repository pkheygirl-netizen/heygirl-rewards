# HeyGirl Rewards v3 — build contract

This file is the single source of truth for names shared between workstreams. Do not rename anything defined here. If something here is impossible, implement the closest working thing and say so in your report.

Store facts: Shopify **Basic** plan, new customer accounts, Dawn theme (Online Store 2.0), cart type **drawer**, currency PKR, timezone Asia/Karachi. App is a single-merchant custom app (Remix, Supabase via service key, BullMQ on Redis, Railway web + worker with `WORKER=1`). The storefront reaches the app only through the app proxy `/apps/loyalty/*` → `/proxy/*`.

## 0. Rules for every workstream

- Stay inside your file ownership (section 6). Never edit another stream's files; if you need a change there, list it in your report.
- Do not run `git commit`, `git checkout`, `git stash` or `git reset`. Do not touch `.env*` or `shopify.app.toml`.
- Never call a tool that changes the live Shopify store (no `graphql_mutation`, product/discount/theme create/update tools). Read-only schema and docs tools are allowed and expected: before writing any Admin GraphQL operation, confirm its exact shape with `mcp__Shopify__graphql_schema` and validate the final operation text with `mcp__Shopify__validate_graphql_codeblocks` when available. Use `mcp__Shopify__search_docs_chunks` for docs. If a tool is unavailable, say which operations are unverified.
- TypeScript strict; no `any` unless unavoidable and commented. Keep existing code style. Every new module gets vitest unit tests next to it (`*.test.ts`), mocking Supabase/Shopify the way existing tests do.

- Money is integer rupees in UI, `numeric` in DB. Points are integers. All "today"/period boundaries and displayed times use Asia/Karachi.
- No secrets in code, logs or client responses.

## 1. Business rules (decided by the store owner)

1. Purchase points: `floor(basis × purchase_points_rate × multiplier)`. Basis = money actually paid for merchandise: order total − shipping − tax − amount paid by gift card. Discount codes (reward codes included) already reduce the total. Awarded only when the order is **fulfilled AND paid AND not cancelled**. COD orders are marked paid by hand 7–10 days after delivery; until then the points are "pending".
2. Multiplier is the one in force when the order was **placed** (campaign active at `placed_at`, including campaigns since ended or deactivated after the fact; Diamond birthday-month 1.2× if no campaign).
3. Auto-consent: placing an order or signing in on the storefront enrols the customer (`consent_given=true`, `consent_source` 'order' | 'signin'). Admin opt-out (`opted_out=true`) stops earning, redemption and re-enrolment. `is_blocked` (fraud) stops earning, redeeming, birthday and referral rewards, and is separate from opt-out.
4. Welcome bonus (`signup_points`, default 1000): once per customer, at first **sign-in** on the storefront only (never at order time). Must also be given to members whose row was created earlier by a webhook or by import with zero points. Added inside the sign-in enrolment itself (18 Nov 2026), so the first `/proxy/customer` answer already includes it; the worker job is only the fallback when that write fails. Idempotent on the ledger key (member, `signup`, customer id); the welcome email is queued once, by the call that wrote the row.
5. Customers with no email (phone only) are enrolled; `members.email` is nullable, `members.phone` stored.
6. Balance never goes below zero. Refund after award reverses `awarded × refunded_basis / earning_basis`, capped at what that order still has un-reversed. Cancellation reverses the remainder. Never more than awarded per order, enforced in the database under a row lock. A cancelled order can never be awarded later.
7. Reward code used on an order that is cancelled **before fulfilment**: return the redeemed points (`redemption_return`), code stays used. No return after fulfilment.
8. Expiry: every positive ledger row of a **Silver** member expires 365 days (`silver_expiry_days`) after `earned_at`; Gold/Diamond do not expire (upgrade clears pending expiry as today). All deductions consume oldest unexpired points first (`points_remaining`, FIFO). Imported Smile balances expire one year from import.
9. Tiers by lifetime spend, thresholds from `app_settings` (`tier_gold_threshold_pkr`, `tier_diamond_threshold_pkr`). Tiers are never taken away. On upgrade issue once: Gold → free-shipping code; Diamond → Rs. `tier_reward_diamond_pkr` (500) code.
10. Referral: friend arrives with `?ref=slug`. When the friend first signs in with a stored ref, record the referral and immediately issue the friend a **free-shipping code** (if `referral_friend_free_shipping`). Friend must have **zero prior orders** and must not already be referred. Referrer earns when the friend's **first** order is fulfilled and paid. If the qualifying order is later refunded in full or cancelled after award, reverse the referrer's points (`referral_reversal`, floor zero). **Fraud rules (owner decision 19 Nov 2026; no network address is compared or stored — behind Shopify's proxy and Railway's edge the app does not see the shopper's address, so the old "same network" rule was removed and `last_seen_ip`, `referred_ip`, `referrer_ip` are no longer written):**
    - **At sign-in, blocked** (`blocked`, no code, no points, `referrals_blocked=true` on the referrer) when: same email after normalising (lowercase, trim, "+tag" dropped for every domain; for gmail.com/googlemail.com dots in the name part removed and googlemail.com = gmail.com) — flag `same_email`; or same phone (last 10 digits) — flag `same_phone`.
    - **At sign-in, held** (`flagged`: the free-shipping code is withheld until staff Approve; `issueReferralFriendCode` refuses a flagged referral) when: similar email — the normalised name part with dots, underscores and hyphens removed (every domain) and trailing digits removed is identical and at least 6 characters (ayesha.khan1@yahoo.com ~ ayeshakhan@gmail.com) — flag `similar_email`; or same full name — first AND last name present on both, compared lowercased with spaces and punctuation removed — flag `same_name`. Blocked beats held.
    - **On the friend's first qualifying order, whether or not she used her free-shipping code** (owner decision 19 Nov 2026, replacing "only the order that used her code": a self-referrer could avoid the check by leaving the code out). The qualifying order is the one that would pay the referrer (her earliest order not cancelled, now fulfilled AND paid); the check runs on it right before the referrer would be paid, unless it already ran on that order (`order_checked_order_id`). It runs for a referral held at sign-in too, so: Approve before she has ordered releases her code as before, and the payment still waits for the check on her qualifying order; a qualifying order whose check finds the referrer's phone blocks the referral, so a later Approve is refused and nothing is paid; Approve of a referral whose own order check produced the hold (address match, gift-phone match, or Shopify never answered) pays without checking again (staff have looked); exception (review 9, widened in review 10): when a referral whose `fraud_flags` contain any reason not set by an order check (sign-in `similar_email`/`same_name`, older reasons such as `same_ip`/`same_network`, or a held row with no reason at all) gets `order_check_failed`, its order id is NOT recorded, whatever its status (also when an Approve has made it pending again and the queued `complete_referral` job fails on every try), so Approve (or a later event, at most once an hour per referral and order, remembered in the worker's memory) runs the check first. A held referral whose check could not record its qualifying order (Shopify did not answer, or an earlier match on another order is kept) is likewise re-checked at most once an hour, never on every event; a pending referral is always checked before payment. **Earlier as well, on any order that used her referral free-shipping code** (order `discount_codes` contains `loyalty_codes.code` of `referrals.friend_code_id`, case-insensitive), at orders/create or the first order event seen, so the tag and alert come early; that order is not checked again when it qualifies. A match already recorded on another order of hers (same address, held) is not overwritten by a clean or unreadable result on the qualifying order: the referral stays held with that finding. What is compared: the order's **shipping** phone and **shipping** address (Admin GraphQL `order.shippingAddress { address1 address2 city phone }`) are compared in memory with the referrer's `members.phone`, Shopify `customer.defaultPhoneNumber`, `defaultAddress`, `addressesV2(first: 10)` and the shipping addresses of `orders(first: 5, sortKey: CREATED_AT, reverse: true)`. Without the `read_all_orders` scope (not requested) Shopify's `customer.orders` returns only orders from the last 60 days, so "last 5 orders" means her last 5 orders placed within 60 days. Phones: last 10 digits. **Phones (owner decision 19 Nov 2026, gift orders):** the order phone equal to one of the referrer's OWN account phones (`members.phone`, Shopify `defaultPhoneNumber`) → `blocked`, flag `same_phone_on_order`, block_reason "The friend's order uses the referrer's phone number", referrer gets nothing, `referrals_blocked` NOT set automatically; equal only to a phone on her saved addresses or her last 5 orders → **held** (`flagged`, flag `same_order_phone_on_order`, reason "The friend's order goes to a phone number the referrer used on one of her earlier orders or saved addresses (could be a gift)"), stored as `order_check = 'same_phone'` with status `flagged` (016's check constraint allows only clear | not_checked | same_phone | same_address; no migration), same tag and Home alert ("… goes to a phone number the referrer used on an earlier order or saved address"); staff Approve or Block. **Address (owner decision 19 Nov 2026, rounds 9, 10 and 11; an address only ever holds, never blocks; address1 and address2 read as one line with a comma between):** each address is read into labelled numbers (house h/hno/"H#"/"H no"/"H.No."/"House No."/villa, street st/str/gali, road, block, phase ph, sector sec/precinct, flat apt/apts/apartment/unit/portion, plot, lane, floor, building/tower, town; a single letter after a label is its value: "Block A"; a label never takes a value across a comma ("Faisal Town, 123-A"), and road/town take only a plain number of at most 4 digits; a label word with one letter wrong/missing/extra/swapped and the same first letter ("Stret 12", "Hous 5") is read as the label when a number follows; "D Block" = "Block D", "10 D Block" = house 10, block D; dwelling letters go after the number: "Flat B-4" = "4-B" = "4B" = "B4"; after phase/block/sector/askari/gulberg/town a single I, V or X is a Roman numeral, "Phase V" = 5, "Askari X" = 10; ii–xx anywhere), sector codes ("G-9/1" = "G 9/1" = "G9/1" = "G-9-1" in any city; in Islamabad also "F-7", "I-8", for the sector letters D, E, F, G, H, I only — "A-12", "B-4" there are homes), unlabelled numbers and letter codes ("Askari 11", "Gulberg III" = 3, "33A", "A-12" = "12-A"; "ext"/"extension" is kept as a mark among them, so "DHA Phase 2 Extension" ≠ "DHA Phase 2"), locality words (after dropping the city field's words, common Pakistani city names, "Pakistan", provinces, filler such as near/opposite/opp/behind/contact and generic words such as town/colony/road/main/mohallah; initials joined, "F.B." = "FB", and "Federal B Area" = "F B Area" = "FB Area"; "-e-" ignored; words split on one side and joined on the other are one word, "Gul Bahar" = "Gulbahar"; words of 6+ letters one letter apart with the same first letter are one word, "Nazimabd" = "Nazimabad"), weak words (north, south, east, west, new, old, gulshan, khayaban, shahrah: "North Nazimabad" ≠ "North Karachi", "Gulshan-e-Iqbal" ≠ "Gulshan-e-Hadeed"), landmark words (masjid, mosque, jamia, madrasa, church, bazar/bazaar, market, hospital, clinic, school, college, university, chowk, stop, plaza, mall, park, station, bank, pump, petrol, store, shop; never a locality word on their own; right before road/rd/street/st/avenue/boulevard/lane they name the road, "University Road" = word "university~road", and before town/colony the town, "University Town" = "university~town", so the two differ), road names (the word before a road word that has no number, or after khayaban/shahrah: "Bank Road", "Khayaban-e-Ittehad") and town names (the word before town/colony: "Johar Town"). Urdu/Arabic-Indic digits are read as 0-9; Pakistani phone numbers are removed by shape with their own digit boundaries (mobile `(+92|0092|92|0)?3xx xxx xxxx`, landline `(+92|0)` + 2–4-digit area code + 6–8 digits = 9 or 10 national digits, any other 10–13-digit run, and any 7–9-digit run, a landline without its area code, so "Johar Town 5761234" is not town 5761234), so "House 12 0321-1234567" keeps 12; then 5-digit postcodes, except right after a label other than road/town ("House 10234" is kept, also at the end of the line — a deliberate reading of the review's "end of line" clause, so "Orangi, House 10234" keeps its house number; "Karachi 75400", "Johar Town 54000" are postcodes). **Review 12:** input caps (only the first 2 ambiguous "H-n" codes get two readings, the rest are bare codes; at most 4 readings; the line is cut to 1,000 characters before and 300 after cleaning, and 40 tokens); "al" is a filler word; both naming a block by word with none shared = no match ("Gulshan Block" ≠ "Nishtar Block"); both carrying an area prefix (north/south/east/west/new/old) with none shared = no match even with the same sector code ("New Karachi Sector 5-C" ≠ "North Karachi Sector 5-C"); "Block 13/D" = "13-D"; a city field of "ICT" = Islamabad; in Islamabad B and C codes from 13 to 18 are sectors ("B-17" = "Sector B-17"; "B-4" stays a home); Kotli and Kotri are never a typo pair (list of real city pairs one letter apart). The city field ignores provinces, "Cantt", "Cantonment", "Capital Territory", "ICT" (alone it is Islamabad), reads Pindi = Rawalpindi, reads a one-letter typo of a known city as that city ("Karchi" = Karachi, "Lahor" = Lahore; only when exactly one known city is that close); cities also match when one letter apart (5+ letters, same first letter), and Islamabad and Rawalpindi are one city for matching. "H-12" (Islamabad sector, or House 12): a sector when a house number is written another way (outside Islamabad a bare code "12H"); house 12 when another sector code is present or "street/st" follows; otherwise both readings are tried and either may match. Match = same city AND EITHER (a) **(owner decision 19 Nov 2026, round 11)** the cleaned lines (phones, postcodes, city/province names and punctuation removed; "H#"/"H no" read as "house"; label spellings otherwise as written) are identical and carry 2 or more labelled numbers — "House 12, Street 5" twice in the same city holds, as does "House 12, Street 5, near Jamia Masjid" twice; a lone labelled number ("House 12") never matches, even written the same; OR (b) the same labelled numbers (a label present on one side only, e.g. a street or floor, = no match; "Street 12, House 5" ≠ "House 12, Street 5"; stand-ins, only for a side with no label of that kind: a house/flat/plot value written bare — "Plot 34" = "34", "House A-12" = "A-12"; a block/sector letter code written bare — "Block R-1" = "R1"; and a bare number+letter for the pair house (or plot) N + block/sector letter L — "120-Y DHA" = "House 120, Block Y", "56-C Bahria Town" = "House 56, Sector C"; each bare value stands in once) AND the same unlabelled numbers AND no road-name or town-name conflict (both name a road, or both a town, and none is the same: "Bank Road, Saddar" ≠ "Haider Road, Saddar", "Khayaban-e-Ittehad" ≠ "Khayaban-e-Shahbaz", "Al-Rehman Plaza, Johar Town" ≠ "… Model Town") AND (a locality word in common OR the same letter-number sector code OR — only when neither side has any locality word — a weak word in common). Landmarks alone never match except through (a): "House 12, Street 5, near Jamia Masjid" vs "H# 12, St 5, near Jamia Masjid" is not a match, just as "House 12, Street 5" vs "H# 12 St 5" is not. An address with no house/flat/plot number, unlabelled number or letter-number code never matches. Address match → `flagged`, flag `same_address_on_order`; approve pays at once if the order already qualifies. Either way the order gets the Shopify tag **"Rewards: check referral"** (`tagsAdd`, needs `write_orders`; the only change the app ever makes to an order — it never cancels or edits anything else) and a Home "Needs your attention" item names the order and links to it in Shopify admin and to the referral, with "Block this referrer" and "Dismiss". Only reason codes are stored (`fraud_flags`, `referrals.order_check` = clear | not_checked | same_phone (blocked own phone, or held gift phone with flag `same_order_phone_on_order`) | same_address, `order_checked_order_id`, `order_tag` = tagged | failed, `alert_resolved_at`), never the phone or address. Shipping details missing although Shopify answered (fields withheld for lack of protected customer data access, ACCESS_DENIED or HTTP 403, no shipping line) → `order_check = 'not_checked'`, logged once, the referral proceeds. The check runs once per order (replays skip it). If Shopify cannot answer (5xx, throttled, any other 4xx, GraphQL errors not about access, an answer without data, or an error of unknown kind), a pending referral is not paid: the follow-up throws and the job is retried; on the points job's **final** attempt the referral is held instead (`flagged`, `order_check = 'not_checked'`, flag `order_check_failed`), so it is never paid without a check and never left waiting unseen; Approve then pays without asking Shopify again. Open `not_checked` referrals (not dismissed or decided, `alert_resolved_at` NULL) are counted on Home ("Needs your attention", link `/app/referrals?check=not_checked`) and in the staff morning email; staff dismiss each one. If `tagsAdd` is throttled or Shopify fails (5xx is repeated, adding the same tag twice is harmless), `order_tag` stays empty and the next event for the order tries again; `failed` only for a permission error or userErrors. **Payment (review 12, migration 017):** paying the referrer is ONE database call, `pay_referral` (section 2), which row-locks the referral, the qualifying order row and the referrer, refuses unless the referral is `pending` (or an older half-done claim for that same order), the referral rule is on, the referrer is not blocked/opted out/`referrals_blocked` and the order is not cancelled or refunded in full, then adds the points (`award_points`, idempotent on member / `referral_earned` / referral id) and sets `completed`, `points_awarded=true`, `reward_points`, `shopify_order_id` in the same transaction; the app reads the order right before the call (cancelled/refunded → nothing added, stays `pending`) and right after it (cancelled/refunded meanwhile → `reverse_referral`, `rejected`, no email), and queues the "referral completed" email (fixed job id) only when its call set `points_awarded` (outcome `paid` or `recorded`), then sets `referrals.completion_email_queued_at` (review 13). **Review 13:** `pay_referral` refuses `order_not_found` when the order row is missing or an order id is null (never a NULL = NULL match); the app throws (retry later, not paid). Every `complete_referral` job has the fixed id `complete_referral-<referral id>` (kept 24 hours after it finishes): a sweep never queues a second one while one is waiting, delayed or running, replaces one that failed for good, and waits out a finished one; Approve and a released claim replace a finished one. The 10-minute `cron_pending_codes` run (after the 017 check, `hg_schema_version` = 17) also (a) queues `complete_referral` for `pending` referrals whose friend's first order (earliest not cancelled) is fulfilled AND paid and not refunded in full, unchanged for 10 minutes, referrer payable and the rule on, at most 100 a run (recovery after 017 lands late or after dead jobs), and (b) queues the "referral completed" email (`referral_completed-<id>`) for referrals completed and paid between 7 days and 10 minutes ago whose `completion_email_queued_at` is still null (at most 100 a run). A claim that cannot go back to `pending` (`conflict`, another open referral for the friend) counts as failed every run and queues nothing; failures in any of the three referral sweeps write `alert:referral_payments`. Reversal is by referral id, whatever the referral's status (`reverse_referral`; `reverseReferralForOrder` finds the referrals naming the order and every `referral_earned` ledger row written for the order), so a referrer never keeps points for a cancelled or fully refunded qualifying order. Half-done claims (`completed`, `points_awarded=false`, `reward_points` set) are no longer created; ones left by earlier code are finished by the cron sweep or an order event only when older than 10 minutes (an order event skips a younger one, reason `claim_in_flight`), through `pay_referral` (from the claim) or `release_referral_claim` (back to `pending` only while no `referral_earned` row exists). A sweep with failures writes the heartbeat `alert:referral_payments` (System health; staff morning email if within 24 hours), removed by the next clean sweep; a claim with no friend id and no ledger row is released. The text that follows describes the earlier (pre-017) mechanism and is kept for the record: paying the referrer claimed the referral first (`pending` → `completed` with `points_awarded=false`, conditional), then added the points (`award_points`, idempotent), then read the order again and, if it was cancelled or refunded in full meanwhile (e.g. staff Approve in the web process racing the worker's cancellation), reverses the referral at once (review 10); Whether the points were added is read from the ledger (`referral_earned` row for member / referral id), not from `points_awarded`: if the row exists, the resume and the reversal record `points_awarded=true` first, then keep the points (the "referral completed" email is queued, under its fixed job id, after `points_awarded` is set and only by the call that set it) or reverse them when the claimed order was cancelled or refunded in full. Every order event of a referred friend's order (orders/create, updated, fulfilled, cancelled, and refunds/create since review 10) retries a missing tag (one database read; Shopify only when a matched order has no tag), whether or not the order has a discount code.
    - Staff can block a referrer (`members.referrals_blocked`) from the Home alert, the Referrals page or her profile, and allow her again from her profile. "Block this referrer" on a Home alert also rejects that referral if it is held (review 10), so it stops counting on Home's "waiting for your approval" line (that line's text is generic: the reason of each held referral is on the Referrals page).
11. Referral reward: standard `referral_points` (6000). Influencer (`is_influencer`, not `influencer_paused`, and now within `influencer_rate_starts_at..ends_at` when set): `round(referral_points × influencer_multiplier)`; if multiplier null, legacy `influencer_referral_rate`; else standard.

**Functions** (plpgsql, all row-locking the member `FOR UPDATE`):

- `award_points(p_member_id uuid, p_action_type text, p_reference_id text, p_points integer, p_expires_at timestamptz DEFAULT NULL, p_shopify_order_id text DEFAULT NULL, p_reason_note text DEFAULT NULL, p_purchase_amount_pkr numeric DEFAULT NULL, p_customer_note text DEFAULT NULL) RETURNS TABLE(awarded boolean, new_balance integer, new_lifetime_spend_pkr numeric)` — same idempotency (unique member/action/reference) and redemption-rejects-when-insufficient behaviour as today. Changes: every positive row gets `points_remaining = points`; every negative row (any action) consumes FIFO across all unexpired positive rows; `expiry` deducts exactly `LEAST(that row's points_remaining, balance)` and marks it expired; floor at zero kept; no longer touches `order_webhook_state`.
- `award_order_points(p_shopify_order_id text, p_member_id uuid, p_points integer, p_basis_pkr numeric, p_multiplier numeric, p_expires_at timestamptz) RETURNS TABLE(awarded boolean, new_balance integer, new_lifetime_spend_pkr numeric)` — locks the order row; returns `awarded=false` if `cancelled_at IS NOT NULL` or already awarded; else writes the `purchase` ledger row (reference = order id), adds `p_basis_pkr` to lifetime spend, sets `points_awarded=true`, `points_awarded_amount`, `multiplier_used`, `pending_points=0`.
- `reverse_order_points(p_shopify_order_id text, p_kind text /* 'refund'|'cancel' */, p_reference_id text, p_refunded_basis_pkr numeric DEFAULT NULL) RETURNS TABLE(reversed integer, new_balance integer)` — locks the order row; on `cancel` sets `cancelled_at`, `pending_points=0`; computes amount per rule 6; writes `refund_deduction` or `order_cancelled` ledger row; bumps `points_reversed_amount`, `refunded_basis_pkr`; reduces lifetime spend (floor 0). No-op (0) when the order row is missing or nothing was awarded.

Stream A must test these three functions against a real Postgres (try the `embedded-postgres` npm package as a devDependency-free scratch install outside the repo, or any Postgres you can start); cover: FIFO across action types, redemption insufficient, idempotent replays, refund then cancel (no double reversal), cancel before award blocks later award, expiry after partial spend, floor at zero, two concurrent reversals.

## 4. Storefront proxy API (stream B owns; JSON, `Cache-Control: no-store`, HMAC verified first)

- `GET /proxy/customer` → guests are never expected to call it. Signed-in: calls `enrolFromSignin`, returns `{ member: { firstName, tier, pointsBalance, pendingPoints, lifetimeSpendPkr, referralLink, birthday: {month, day} | null, canSetBirthday, isInfluencer, optedOut, blocked }, codes: [{ id, code, kind, discountPkr, expiresAt }], social: { instagram, facebook, youtube: 'available'|'claimed' }, review: { eligible, pending }, nextExpiry: { points, at } | null }`. `pendingPoints` = sum of `order_webhook_state.pending_points` for the customer where not cancelled and not awarded.
- `GET /proxy/history?filter=all|earned|redeemed|referral|other&page=` → rows `{ id, type, label, points, at, note }` where `note` is `customer_note` only (never `reason_note`).
- `POST /proxy/redeem {points}` → `{ ok, code, discountPkr, expiresAt }` or `{ ok:false, error }` (one error field name everywhere: `error`).
- `POST /proxy/social {platform}` → `{ ok, status: 'awarded'|'already_claimed', points }` or `{ ok:false, error }`.
- `POST /proxy/review` → `{ ok }` or `{ ok:false, error }` (no release time: staff approve each claim, rule 14).
- `POST /proxy/birthday {month, day}` → `{ ok }` or `{ ok:false, error }`.
- `POST /proxy/referral {slug}` → `{ ok, status, friendCode? }`.
